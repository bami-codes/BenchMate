# Film review — 4411fdc / supplied benchmate.mp4

검토 대상: 사용자가 제공한 `benchmate.mp4`, 최신 main `4411fdc`,
공개 사이트 배포 `2151329` / gh-pages `b55aecc`.
영상 SHA-256: `063f88262a99aad819f57926ac8e0fe00a73f64a0ecb28536aa48d93b1ff2790`.
원본 MP4와 DNG는 이 검토에 추가하지 않았다. 아래 증거는 MP4의 메타데이터 없는 프레임 파생본이다.

실험 기록·모델·사이트·영상 소스는 직접 수정하지 않았다. 모델·음성 생성·하드웨어 호출은0회다.
Claude 소유 파일에 대한 수정 요청이며, 원본 기록이나 판정을 바꾸라는 요청이 아니다.

## 확인된 개선과 배포 상태

- MP4는1920×1080,60fps, 영상168초다. AAC는169초로 컨테이너 전체는2:49다.
  04가약26초에 먼저 시작하고, 01은약76초에 시작한다. 제공 JPG는 이전 순서의 콘택트시트이므로
  이번 평가는 실제 MP4를 기준으로 했다.
- 공개 `data/cases.json`과 `assets/replay.js`는 최신 main 내용과 바이트 단위로 일치한다.
  05의 외부 저항20kΩ, 04의 불필요한 읽기 절차 제거, 판정 제목 교체는 배포되어 있다.
- main `4411fdc`, `2151329`, `13da928`의 Tests는 모두 성공했다.
- 04의111.02 /79.34 /73.72mV 및 예약 검증 최악 구간5.19 /4.05mV는 기록 기반이다.
  01의4.71kΩ 관측, 범위 동결→SAM 지목→읽기→공개 순서와 마지막 복원 카드도 실제 영상에 있다.
- 아래 문제들은 기존 재생20/20 검사에서 확인하지 않는 영상 전용 프레임 상태와 회로도 표시 문제다.

## P1-A — 04의 제안 다이오드가 그림에서는 REF에 연결되지 않음

**시각 증거:** [00:54 프레임](../review-assets/2026-11-04-film-review/case04-proposal-54s.jpg).

`site/assets/common.js`의 `netlistSVG()`는 OUT에 두 병렬 분기가 있으면
R2를x610, D1을x730에 배치한다. 그런데 REF 수평선은x700에서 끝나므로
다이오드 하단과REF 사이가30 SVG 단위 떨어진다. D1 라벨x774도viewBox 너비760 밖이다.
핵심 클라이맥스에서 다이오드가 떠 있는 회로와 잘린 라벨을 보여준다.

**실제 넷리스트는 정확하다:** 기록의 추가 부품은
`D1 {kind:D, a:OUT, b:REF, model:generic_diode}`다. 실험·모델이 아니라 표시 함수 오류다.

요청: REF선 범위와viewBox를 실제 병렬 분기 및 라벨 범위에 맞춰 계산한다.
영화와 사이트가 같은 함수를 쓰므로 둘 다 반영하고, 병렬 분기1/2/3개에서도 잘림·단선이 없는지 확인한다.
예측/넷리스트 원본은 바꾸지 않는다.

## P1-B — 병렬 렌더 경계에 실제 한 프레임 점프가 있음

**영상 증거:** [55.9833→56→56.0167초 /111.9833→112→112.0167초](../review-assets/2026-11-04-film-review/parallel-chunk-boundaries.jpg).

00:56.000과01:52.000에서만 카메라가 노트 위쪽으로 크게 튄 뒤 다음 프레임에 복귀한다.
168초를3개 작업으로 나눈 청크의 첫 프레임과 정확히 일치한다.

최신 stage를 새 브라우저에서 열어 같은 `frame(t)`를 두 번 호출해 재현했다:

| t | 첫 호출 world transform의Y | 같은t 재호출의Y | 동일 프레임 이미지 |
|---|---:|---:|---|
|56|−359.30px|−1498.95px|서로 다름|
|112|−364.20px|−2015.30px|서로 다름|

`window.frame`이 `applyCam(t)`를 먼저 호출하고, 이후에 `Scn`이 카드 높이를 갱신한다.
독립 청크의 첫 호출은 아직 펼쳐지지 않은 카드 위치로 카메라 앵커를 계산한다.

요청: 해당 시각의 장면·카드 상태와 레이아웃을 먼저 확정한 뒤 카메라 앵커를 계산한다.
필요하면 레이아웃 측정 단계를 명시적으로 분리한다. 단순한300ms 대기로는 이 순서 문제가 해결되지 않는다.
새 페이지에서 바로 렌더한56/112초와 순차 재생으로 도달한 같은 프레임이 같아야 한다.
수정 후 독립 청크 경계를 포함해 MP4를 재확인한다.

카메라만 안정시키고 끝내지 않는다. 새 페이지에서108초로 바로 가면 이미 탈락한
As drawn/C1 계기에도 과거 점수 대신 `waiting`이 남는다. 이전 단계를 실제로 거쳤는지와
관계없이, 과거 탈락 수치·테이프·현재 읽기 모드를 해당 시각의 기록에서 복원해야 한다.

## P1-C — 읽기 계기의 kΩ 눈금 아래에 이전 mV 오차가 표시됨

**영상 증거:** [01:48 프레임](../review-assets/2026-11-04-film-review/case01-reading-108s.jpg).

탈락한 `R1 changed` 계기는kΩ 눈금과23.2–27.9 범위를 표시하지만,
아래 readout은 `3.25mV / step3 · worst region`이다. 관측값은4.71kΩ다.

새 브라우저에서 같은 `frame(108)`를 두 번 호출하면:

1. 첫 호출: R1 changed readout = `4.71kΩ / reading`.
2. 두 번째 호출: 같은 계기 readout = `3.25mV / step3 · worst region`.

`Scn.s4`의 매 프레임 학습 점수 갱신이 읽기 모드의 값을 덮어쓴다.
`_dead` 플래그 때문에 그 뒤 `setReading`은 다시 실행되지 않고, 이전 읽기 판정 테이프만 남는다.

요청: 읽기 단계에 들어간 뒤에는 해당 계기를 파형 오차 갱신에서 제외하고,
관측값·단위·바늘·탈락 상태를 그 시각의 읽기 상태에서 매번 일관되게 계산한다.
한 번만 실행되는 `_band/_dead` 상태에 의존해 의미가 달라지지 않게 한다.
새 페이지 직접 렌더/반복 호출/순차 도달에서108초의 표시가 같아야 한다.
이는 실제 읽기값이나 판정의 변경이 아니라 그 값을 제대로 보여주는 수정이다.

## P2 — 수상 목표로 다듬을 우선순위

1. **도입 회로도를 첫 사례와 맞춘다(00:11–00:25).** `buildB`는 아직
   `assets-schem01.png`의RC 회로를 보여주는데 첫 진단은04 분압회로다.
   도입을04 설계로 맞추거나 공유 벤치 소개임을 분명히 해, 관객이 시작부터 다른 회로를 기억하지 않게 한다.
2. **실패 자막과 계기 판정을 동기화한다(약00:40–00:44).** 현재111/79/73mV와
   “every value explanation fails” 자막은s3 로컬13.8초에 시작한다. 바늘 갱신은16.4초부터,
   완전한 판정은17.8초, 탈락 테이프는18초부터다. MP4의00:42에는 실패 자막과 `waiting` 계기가 공존한다.
   파형 스윕→점수 계산→붉은 바늘/탈락→제안의 인과가 화면에서도 읽히게 맞춘다.
3. **읽기 장면의 내부 ID와 긴 문장을 일반 표현으로 바꾼다(01:30–01:50).**
   `external_equivalent:changed:R1`은 사건 ID로 보존하되 화면에는
   `Extra resistance before R1` 같은 문구를 쓴다. 읽기 카드의 주 정보는
   `R1 itself changed:23.22–27.95kΩ` / `Extra series resistance:4.36–5.05kΩ` 두 범위와
   `Read R1:4.71kΩ`다. 원문 인용·세부 표를 전부 크게 보여주기보다 핵심을 우선 읽히게 한다.
4. **마무리16초 중 일부를 밴드·복원 결과의 정지 시간으로 옮긴다.** 현재 복원 카드가
   제대로 보이는 시간은약01:56–01:58로 짧다. 첫 전원 인가 시 사용자가 얻는 결과를 유지하면서,
   종료 카드를8–10초로 줄이면 핵심 증거를 더 편하게 읽을 수 있다.
5. **점수의 뜻을 그 장면에서 표시한다.** 학습 중 후보 재적합과 측정 후IN 조건부 점수는
   뒤의 기록 장면에 설명되어 있다. 실제 점수 카드에도 `Training fit · measured IN`,
   예약 검증에는 `Frozen-model check · measured IN` 등으로 짧게 구분하면
   측정 전 명령 입력 예측과 같은 점수라고 오해할 여지가 줄어든다. 두 원본 점수는 유지한다.

## 음성과 최종 내보내기

- 이번 검토 파일로 내레이션 발음·연기·믹스를 최종 승인할 수는 없다. 원격
  `voice/durations.json`은 빈 객체이고, 최종 음성 클립은 아직 반영되지 않은 단계다.
- 현재 `video/film/narration.txt`는405단어이며150wpm 단순 계산으로162초다.
  일괄 속도 증가를 전제로 삼지 말고 실제 클립을 붙인 뒤 필수 홀드와 전체 길이를 확인한다.
- 장면 전체 길이를 음성 길이에 비례해 늘리는 것만으로는 내부 단어와 키프레임이 맞지 않는다.
  실제 발화의 `forecast`, `measured`, `diode`, `4.71`, `seal`, `no mismatch` 시점을 기준으로
  중요한 동작을 맞춘다. 음성이 확보되기 전 재렌더를 최종본으로 확정하지 않는다.
- 음성 기준은 **`video/film/narration.txt`**다. `video/film/README.md`는 아직
  `../v2/narration.txt`와옛 shot list를 가리킨다. `voice_durations.py`의PLANNED도
  옛 순서의11/16/58/38/22/14/11이어서 현재10/16/50/42/16/18/16과 다르다.
  최신 단일 기준으로 동기화하고, 누락된 음성 파일도 감지한다.
- 현재 `mux.py`는 영상보다1초 긴bed를 만들고 종료 길이를 제한하지 않아
  컨테이너가 영상168초보다 긴169초다. 최종 스트림 끝을 의도한 길이에 맞추고,
  mux 후 실제 파일의 영상/음성/전체 길이가 모두180초 이내인지 검사한다.

## 이번 검토의 범위

전체 구성은6초 간격 프레임으로 훑고, 주요 구간은 원해상도와1/60초 경계 프레임으로 확인했다.
최신 stage에서 독립 프레임 재현 검사를 추가했다. 움직임·음성의 최종 감상 검토를 대신하지 않으며,
새 음성·음악·회로 모델·하드웨어 실험을 생성하지 않았다.
