# 넷리스트 진단 v1 — 21:55 방향의 첫 구현

> LED까지 포함하는 현재 여섯 사례 실행기는 [v2](netlist-diagnosis-v2-led.md)다.
> 이 문서와 v1 실행기는 비LED 다섯 사례의 보존된 버전으로 남긴다.

11/2 Codex. [최신 방향](2026-11-02-direction.md)의 서로 다른 실제 회로를 대상으로 한다.
이전 사전 확인의 "값만 다른 RC 여섯 개"는 채택하지 않았다.

**완료 범위:** 비LED 다섯 회로의 새 영어 진단 엔진, 유료 호출 없는 모의 실행,
고장/복원 재실행, 구분 가능성 점검, 새 수동 배선 확인 경계와 가짜 시리얼 검사.
**미실행:** 실제 Spark 결정, 새 회로도 비전, SAM/사진 호출, 실물 배선·계측·펌웨어 업로드.
LED/BJT는 아래 별도 단계다. 부품 BC547과 LED는 사용자가 모두 보유했다고 확인했다.

## 새 구현과 보존

- `src/benchmate/netlist_diagnosis/`에 별도 버전으로 추가했다. 기존 동결 53파일은 수정하지 않았다.
- `physical_netlist.simulate_physical_netlist`의 측정 IN/PWL·타이밍·ngspice 실행을 재사용한다.
  B5의 `rank_info`와 훈련 전용 맞추기 방식을 사용한다. 기존 B5 맞추기는 무부하이고 R/C가 최대 두 개여서,
  알려진 부품을 고정하고 한 부품만 변화시키는 맞추기 층을 새로 만들었다.
- 기존 전체/구간 9 mV 채점(`d01_repair.command_score`)과 `agent.drive_agent`를 재사용한다.
  전체 RMS만으로 판정을 바꾸지 않는다.
- 프롬프트, 도구 설명, 보고 및 작업자 선택문은 영어다. 과거 한국어 기록은 그대로 보존했다.
- 기존 펌웨어와 계측 가드를 재사용하는 `PhysicalNetlistBench`를 추가했다.
  실제 시리얼 대신 가짜 보드로만 검증했다. 전압 범위·펌웨어는 확대하지 않았다.

## 진단이 진행되는 방법

1. 사람이 확인한 의도 회로 목록을 받는다. 기존 Spark 판독 결과는
   `design.from_transcription()`으로 가져오고, 연결·값·포트를 실제로 확인한다.
   `design.review()`는 R/C/D와 명시적인 IN–OUT 점퍼 W1을 지원한다.
   기존 이미지 판독 도구는 W를 출력하지 못하므로, 접촉 사례의 두 포트가 같은 선이라는 사실은 확인 단계에서 W1로 명시해야 한다.
2. 설계 그대로와 R/C 한 부품의 값만 바뀐 후보를 만든다. 다른 알려진 부품은 고정한다.
   훈련 OUT만 사용해 값을 맞추며, 수치 실패·시간 초과를 회로 탈락으로 세지 않는다.
3. Spark가 공통 메뉴에서 매번 **한 실험**을 고른다. 처음부터 모든 메뉴가 열려 있고,
   부하부터 선택해도 작업자 확인을 거쳐 처리한다. 반복도 최대 세 번의 훈련 예산을 쓴다.
4. 모든 후보가 수치적으로 맞춰졌고 전부 부적합할 때만 구조 제안을 연다.
   Spark가 낸 연결을 그대로 시뮬레이션한다. 추가 R/C 최대 두 개와 공유 다이오드 IS/N만 맞추며,
   엔진이 정답 구조를 대신 삽입하지 않는다. 제안 최대 두 번이다.
5. 검증 요청을 받으면 모델·값과 두 예약 입력의 **명령 입력 예측**을 먼저 저장하고 공개 확인을 받는다.
   이후 새 측정 IN으로 조건부 예측을 계산하되 예약 OUT은 맞추기에 넣지 않는다.
   명령 곡선 점수와 조건부 점수를 각각 보존한다. 물리 실행에는 원격 공개 확인이 필요하다.
6. 예약 두 검사까지 통과한 후보의 교집합을 낸다. 여러 후보면 구분 불가이며,
   정상 후보가 남으면 "선택한 검사에서 불일치가 검출되지 않음"이다.
   최저 오차 후보를 임의의 정답으로 고르지 않는다. 검증 뒤 추가 학습·재시도는 없다.

실행기가 훈련 순서를 정하지 않는다. 무료 검증에서만 `ScriptedController`가 같은 세 조건을
고르는 시험용 역할을 맡았다. 그 이유 문장에는 SOFTWARE SCRIPT가 붙고 Spark 결정으로 표시하지 않는다.
모델 문맥에는 사례명·포럼 링크·정답표·배선 좌표·사진·이전 세션이 들어가지 않는다.

## 공통 메뉴와 측정 범위

훈련 메뉴: 무부하/9.99 kΩ 부하 스텝(±0.2 V 또는 ±0.5 V),
무부하 1 Hz 사인(0.2 V 또는 0.8 V), 무부하/부하 5 Hz 사인(0.15 V).
스텝은 0.5 ms × 512점, 1 Hz는 4 ms × 512점, 5 Hz는 2 ms × 512점이다.
예약 조건은 훈련에 없는 무부하 ±0.35 V 스텝과 0.65 V / 5 Hz 사인이다.

R 범위는 기존 검증기의 1–100 kΩ, C는 1 nF–10 µF를 유지한다.
노드 IN/OUT/REF/N1/N2, 총 6요소까지이며 임의 SPICE 문장·코드·파일 경로는 받지 않는다.
5V/접지/BJT는 이 범위에 포함하지 않는다.

## 회로도 작업에 쓸 설계값

REF는 기존 약 1.6 V의 기준점이며 GND가 아니다. 다음 연결은 설계/시뮬레이션 명세다.
실제 배선 작업은 별도의 승인과 확인 뒤에 한다.

| 사례 | 모델 입력용 의도 회로 | 작업자만 아는 고장 | 복원 대조군 |
| --- | --- | --- | --- |
| 핀 출력 저항 | R1=4.7 kΩ IN–OUT, C1=1 µF OUT–REF | 측정 IN 뒤/미니보드 앞에 20 kΩ 추가(10 kΩ 두 개 직렬) | 추가 R 제거 후 새 세션 |
| 센서 필터 | R1=10 kΩ IN–OUT; Cfilter=1 µF, Cbypass=0.1 µF(104), Rload=22 kΩ는 모두 OUT–REF | Cfilter만 0.47 µF(474)로 교체 | 1 µF로 복원 후 새 세션 |
| 555 타이밍 사슬 | RA=10 kΩ IN–N1, RB=10 kΩ N1–OUT, C1=1 µF OUT–REF | RA 하나만 2.2 kΩ로 교체 | 10 kΩ로 복원 후 새 세션 |
| 꺼진 칩 입력 | R1=4.7 kΩ IN–OUT, R2=22 kΩ OUT–REF | OUT 애노드/REF 캐소드 방향 외부 다이오드 | 다이오드 제거 후 새 세션 |
| 접촉 저항 | IN–OUT 점퍼 W1; Rload=10 kΩ와 Cdecouple=1 µF가 OUT–REF 병렬 | 측정 IN과 미니보드 사이 10 kΩ 추가 | 추가 R 제거 후 새 세션 |
| 흐린 LED | BC547·LED·베이스 R·LED R | 베이스 저항 과다 | 아래 별도 단계 |

555는 실제 555 발진기가 아닌 타이밍 사슬 부분이다. 원문은 두 저항이 모두 잘못됐지만,
현재 한 부품 변화 가설을 시험하기 위해 하나만 바꾼다. 그 차이를 Changed에 쓴다.
센서 필터도 MPU6050 내부 레귤레이터 안정성이나 가속도 잡음까지 재현했다는 뜻이 아니다.

계측 보드와 미니보드의 기본 세 선은 기존 IN=A35→미니 A3, OUT=D30→미니 A8,
REF=C50→미니 A13을 기준으로 한다. 숨긴 R은 **IN 측정점 뒤**에 있어야 조건부 분석으로 관측된다.
전원·소자 방향과 실제 빈 구멍은 새 작업자 확인 전까지 추정하지 않는다.
회로도에는 숨긴 부품, 원인명, 포럼 제목이나 칩 내부를 넣지 않는다.

## 측정으로 구분되는 것과 남는 것

| 사례 | 모의 검사 결과 | 측정만으로 남는 한계 |
| --- | --- | --- |
| 핀 출력 저항 | 실효 직렬 경로 R 증가 | R1 자체가 큰 것과 보드 밖 직렬 R은 동일 응답. R1 실제 값은 사진/별도 측정으로 확인 |
| 센서 필터 | 이번 1→0.47 µF 변화는 Cfilter 가설로 좁힘 | 두 병렬 C의 합만 관측. 겹치는 양수 변화 범위에서는 둘을 구분할 수 없음 |
| 555 사슬 | RA 또는 RB 감소, 구분 불가 | 사슬 합만 관측. 부하·주파수를 바꿔도 어느 저항인지 구분 불가 |
| 꺼진 칩 입력 | 단일 값 후보 전부 실패 후 다이오드 제안이 예약 검증 통과 | 다이오드가 유일한 구조이거나 실제 칩 내부가 그 구조라고 단정할 수 없음 |
| 접촉 저항 | 단일 값 후보 전부 실패 후 직렬 R 제안이 예약 검증 통과 | 접촉/점퍼 원인 위치는 모름. 정상의 이상적인 IN–OUT 연결에서는 병렬 R/C가 측정 IN→OUT에 보이지 않음 |

센서의 Cfilter+Cbypass 합은 설계 1.1 µF, 고장 0.57 µF다. Cbypass=0.1 µF 하나만 줄여서는
그만큼 감소할 수 없으므로, **알려진 설계값·한 부품 고장·양수 C 가정 아래** 이번 고장은 Cfilter로 좁혀진다.
그래서 이 값으로 "반드시 사진이 있어야 둘을 가른다"고 주장하면 안 된다.
필터 C를 1.2 µF로 늘린 경우와 바이패스 C를 0.3 µF로 늘린 경우는 합이 같고 실제로 구분되지 않는다.

시뮬레이터는 입력에 병렬인 가지를 조건부 출력에서 관측 불가로 기록한다.
그 가지가 실제로 없다는 뜻이 아니며 총 입력 전류도 알아냈다는 뜻이 아니다.
고정 PWL 모서리의 가짜 충전 전류를 실물 전류 안전성 검증으로 사용하지 않는다.
접촉 사례의 점퍼도 큰 가짜 직렬 저항으로 바꾸지 않고 ngspice의 명시적 0 V 연결로 실행한다.

## 실행과 증거

```sh
.venv/bin/python scripts/netlist_diagnosis.py catalogue
.venv/bin/python scripts/netlist_diagnosis.py evaluate --output runs/NEW_UNUSED_DIRECTORY
.venv/bin/python scripts/netlist_diagnosis.py identify --output runs/NEW_UNUSED_RESULT.json
.venv/bin/python -m pytest -q tests/test_netlist_diagnosis.py
```

`evaluate`는 다섯 고장과 각각의 복원, 총 열 개의 새로운 모의 세션이다. 비용/외부 요청/하드웨어 0회다.
`identify`는 같은 응답을 만드는 다른 부품값/연결을 모든 공통 메뉴에서 직접 비교한다.
예전 결과를 덮어쓰지 않고 새 경로를 요구한다.

소스 해시를 고정한 개발 실행의 열 건이 모두 예상 판정을 냈다. **Spark 성능 10/10 또는 실물 정확도 100%가 아니다.**
같은 ngspice가 정답 회로와 예측 회로를 계산한 개발 검사이며, 별도로 독립 RC 해석식과
Shockley 방정식의 수치 근 찾기로 맞추기를 검사했다.
기존 모듈을 포함한 관련 Python 검사 87개, JS 검사 7개가 통과했다.
첫 시도·연결 가정 변경 전 시도·최종 소스 고정 시도와 동등성 점검은
[공개 개발 기록](../examples/netlist-diagnosis/2026-11-02/REPORT.md)에 보존한다.

새 실제 회로도 이미지 판독과 사용자의 확인 파일을 받은 뒤
`prepare --reviewed-design FILE --output NEW_DIRECTORY`로 새 프로토콜을 만들 수 있다.
준비는 승인이나 실행이 아니다. 실제 실행 전 API 호출/비용 한도, 프로토콜/소스 해시,
초기 배선 확인, 실제 직전 부팅 ID와 원격 예측 공개 경로를 확정해야 한다.
CLI는 지금 실제 시리얼 실행을 노출하지 않는다. 물리 어댑터를 연결하는 실행 단계는 별도 승인 후 진행한다.

## LED 마지막 단계

추가 4–8시간 추정은 부품이 있다는 조건이고, 사용자가 BC547과 LED 보유를 확인했다.
현재 R/C/D 검증기에 Q를 억지로 넣거나 가짜 RC 결과로 대체하지 않는다.

1. 5V·GND·REF 경계와 LED 저항/부하 전류, BC547 핀 배치를 먼저 확정.
2. BJT와 LED의 새 허용 모델 및 정상/고장 합성 검사. 베이스 R과 BJT 이득의 혼동도 보고.
3. LED 하나의 낮은 전류에서는 원문의 4.7 kΩ도 충분할 수 있으므로,
   원문 수치만 복사하지 않고 정상/고장 상태가 실제로 갈리는 부하·저항값을 확인.
4. 기존 LM358 측정 경로의 0V/5V 부근 한계와 필요한 감쇠/경로를 결정.
   펌웨어 한도 확대만으로 아날로그 범위가 넓어지지 않는다.
5. 새 펌웨어 파일·프로토콜·가짜 전송 검사 및 컴파일. 실제 업로드·5V 연결·계측은 사용자 승인 뒤에만 한다.

사진 단계는 Claude의 OpenCV 산출물을 받은 뒤 별도로 이미지 수·SAM/Spark 호출 수·비용을 제시한다.
이번 엔진 개발에 사진/유료 호출 승인은 포함하지 않았다.
