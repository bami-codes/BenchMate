# D01 수리 실행 안내 — 최종 스프린트의 첫 실물 작업

**실행기와 모의 검증은 준비됐다. 실제 Spark 수리 실행은 아직 하지 않았다.**
[최종 스프린트](final-sprint.md)에 따라 **D01 수리를 먼저, B5를 다음**에 한다.
이 문서나 이전 완료 보고만으로 현재 배선·USB 상태를 가정하지 않는다.

## 1. 명목 설계 확인

시작값은 **의도한 회로도**에서 읽은 10 kΩ / 1 µF다. 조립 사진에서 읽은
`105J100`은 보이는 부품의 표기이며, 회로의 원래 설계나 숨은 연결을 증명하지
않는다. 사진에서 두 C가 보인다고 명목 설계를 2 µF로 바꾸지 않는다.

`scripts/known_design.py serve --demo`의 기록된 회로도 판독을 불러온 뒤 사람이
원래 설계의 R·C·연결과 검토 메모를 확인해 저장한다. `confirmed-design.json`을
받아 사용한다. 이는 새 비전 호출이나 전기적 검증이 아니다. 현재 수리 실행기는
이 고정된 10 kΩ / 1 µF 개발용 시편만 지원한다.

## 2. D01 시작 준비

실행 담당자의 요청이 오면 USB를 빼고 LED가 꺼진 뒤 작업한다.

1. 다이오드가 설치돼 있다면 양쪽 다리 모두 제거한다. 아직 회로 밖이라면 그대로 둔다.
2. 미니보드의 원래 C를 **D8–D13**, 추가 C를 **I8–I13**에 설치한다.
   원래 R **B3–B8**, E8–F8·E13–F13, IN·OUT·REF 연결선은 유지한다.
3. 큰 보드의 **11번 B28–B35**, **14번 B50–B23**, D55–D60 9.99 kΩ,
   C23–A60 REF선을 유지한다. **996 Ω 션트, A55–C35 IN 분기,
   E30–A55 OUT 부하 점퍼는 없어야 한다.**
4. 무전원 통전으로 원래·추가 C의 금속 다리 **D8↔I8**, **D13↔I13**이
   각각 삐인지, 미니 D8↔큰 E30 OUT과 미니 D13↔큰 D50 REF가 삐인지 확인한다.
   C의 양 끝끼리 삐여야 한다는 뜻이 아니다.
5. 실제 두 C 상태를 위에서 사진으로 남긴다. 사진 전송은 별도 범위다.
6. 프로브를 제거하고 같은 USB에 재연결한다. 실제 완료한 배선·통전 결과와
   명목 10 kΩ / 1 µF 확인을 보고한다. 새 보고의 원문과 검토 파일 해시를 기록한다.

멀티미터 전압 중심 맞춤은 요청하지 않는다. 새 부팅, ADC 정지 구간, 레일,
타이밍과 A4 변화 가드가 통과해야 자극을 보낸다. 통과하지 못하면 중단한다.

## 3. Spark의 부하 요청

Spark가 무부하 스텝으로 시정수를 관찰한 뒤 출력 부하를 선택하면 멈춰 요청한다.
USB를 빼고 LED가 꺼진 뒤 **큰 E30–A55 OUT 부하 점퍼만 연결**한다. IN 분기는
계속 없어야 하고 두 C와 나머지 배선을 유지한다. 같은 USB 재연결과 실제
완료 보고 뒤 새 부팅에서 부하 스텝을 측정한다. 이어 0.15 V / 5 Hz 사인으로
같은 모델을 검사한다. 여기까지는 진단이며 수리 완료가 아니다.

## 4. Spark의 수리 요청과 예측 공개

두 진단 검사에서 C 변화 후보만 지지될 때만 Spark가 명목 C 복원을 요청할 수
있다. 다른 후보나 모호한 결과면 수리를 진행하지 않고 보류한다.

실행기는 **복원 모델과 수리하지 않은 모델**, 부하 스텝과 **0.10 V / 4 Hz 사인**의
명령 입력 기준 곡선을 먼저 저장·커밋·푸시한다. 원격 커밋 확인이 실패하면
작업자 수리 요청을 내지 않는다. 전체/모든 구간 9 mV 기준과 모델값은 고정한다.

공개 확인 뒤 요청이 오면 USB를 빼고 LED가 꺼질 때까지 기다린다.
**미니 I8–I13 추가 C만 양쪽 다리 모두 제거**한다. 원래 D8–D13 C, B3–B8 R,
큰 E30–A55 OUT 부하, 9.99 kΩ, REF선, 11·14번 점퍼와 나머지 연결은 유지한다.
같은 USB 재연결 후 실제 완료 보고를 한다. 이 구멍 정보는 모델에 보내지 않는다.

## 5. 수리 후 검사

수리 전과 다른 새 부팅을 요구한다. 그 새 부팅에서 스텝과 4 Hz 사인을 측정하며
두 검사 사이에는 USB·RESET·배선을 바꾸지 않는다. 각각 별도 HOLD 원점을 쓰고,
수리 후 평가 대상 OUT으로 모델·이득·바이어스를 다시 맞추지 않는다.

복원 모델이 **두 파형의 전체와 모든 구간**에서 9 mV 이내이고, 수리하지 않은
모델이 적어도 한 조건에서 실패해야 수리 응답 변화가 검증된다. 이것은 측정 IN을
받은 **조건부 비교** 판정이다. 미리 공개한 **명령 입력 곡선**의 점수도 별도로
보존한다. 둘이 다르면 차이도 보여주며 사전 곡선을 실측에 맞게 덮어쓰지 않는다.
두 독립 절대 전압 원점을 모르므로 사전 곡선은 HOLD 대비 **증분 전압**이다.

중단·실패·잘못된 확인·예상 밖 재부팅을 보존한다. 자동 재시도·RESET·재ARM은
없다. 종료 후 출력 상태 기록을 확인하고 USB를 분리한다.

## 실행 담당자용 파일

- 고정 프로토콜·API 범위·검토할 판독·빈 초기 보고:
  `examples/d01-repair-protocol/2026-11-01-repair-first/`
- 실행기: `scripts/physical_d01_repair.py`
- [정상 및 실패 모의 기록](../examples/d01-repair-rehearsal/2026-11-01/README.md)

초기 보고는 `fixture=unloaded`, `USB_connected=true`, `USB_off_wiring_confirmed=true`,
`nominal_design_confirmed=true`, 실제 검토 JSON의 canonical SHA-256와 `verbatim`이
필요하다. 빈 템플릿의 `template_only`를 실제 확인 없이 바꾸지 않는다. 직전 부팅은
마지막 실제 계측 기록의 값으로 넣는다. 예정됐지만 하지 않은 B5의 부팅을 만들지 않는다.

```sh
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python scripts/physical_d01_repair.py run \
  --bench physical --provider meta --execute --publish-freeze \
  --protocol examples/d01-repair-protocol/2026-11-01-repair-first/protocol.json \
  --reviewed-design PATH_TO_ACTUAL_CONFIRMED_DESIGN \
  --vision-record examples/vision-spark/2026-10-31/20261031T060049-13a656638d/attempts/20261031T060050-8f3ccccdc9 \
  --initial-report PATH_TO_FRESH_REPORT --previous-boot-id ACTUAL_LAST_BOOT_ID
```

`operator-request.json`의 실제 요청 ID·action과 일치하는 응답 파일을 해당 실행
폴더에 쓴다. 수리 응답에는 `prediction_sha256`, USB-off/재연결, 추가 C 제거,
원래 C·부하 유지, 나머지 배선 유지가 각각 true여야 한다. 사용자 완료 보고를
대신 생성하지 않는다. 30분 내 응답이 없으면 종료하며 시간이 승인이 되지 않는다.

Meta는 `muse-spark-1.3`, medium, 최대 8회다. 명목 R/C와 새 시정수·오차·검증
요약만 보낸다. 원시 ADC, 이미지, 구멍 안내, 이전 시편 결과, 로컬 파일은 보내지
않는다. 이 새 실물 실행 범위를 시작 전에 승인받는다. 준비와 모의 검증에는
유료 요청이나 하드웨어 명령이 없었다.

## 촬영과 다음 작업

부하 점퍼 연결과 추가 C 제거를 실제로 하는 순간을 촬영한다. 폰은 가로로 고정하고,
맥 화면 녹화도 측정 전에 시작한다. 화면은 읽기 전용 `benchmate watch RUN_PATH`로
본다. 원본 영상은 `video/raw/`에 두고 공개하지 않는다.

수리가 실제로 끝난 뒤 남은 배선을 확인한다. USB를 빼고 LED가 꺼지면 원래 C
D8–D13과 OUT 점퍼 E30–A55를 양쪽 끝 모두 제거한다. 추가 C가 이미 빠졌는지도
확인하고 B5 시작 상태 전체와 대조한다. 수리가 중단됐다면 남은 실제 배선부터 확인한다.

B5는 첫 실물 실행 시작부터 3시간 또는 실물 실행 기록 2회 중 먼저 도달하는 한도로
멈춘다. 통신·가드 실패도 횟수에 포함한다. 전체 하드웨어 동결은 11/2 23:00 KST다.
